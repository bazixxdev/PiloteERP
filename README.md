# Pilote — prototype de l'outil de pilotage des projets (CRESS)

Prototype fonctionnel, données 100 % fictives. Next.js 15 · Prisma + PostgreSQL · Tailwind + shadcn/ui.

1. Un PostgreSQL local (Homebrew `postgresql@18` sur le poste de Gaël, ou `docker compose up -d` avec le `docker-compose.yml` fourni). Une fois : `createdb pilote_dev && createdb pilote_test` avec un rôle `pilote` / `pilote` (`create role pilote login password 'pilote' createdb`). `cp env.example .env` (la `.env` n'est pas versionnée ; le gabarit liste toutes les variables, les secrets de production ne vivent que sur le serveur).
2. `npm install` — installe les dépendances et génère le client Prisma.
3. `npx prisma migrate deploy` puis `npm run seed` — applique le schéma et charge les données de démonstration (15 personnes, 22 projets, 52 éditions). **Client** (lot I) : `NEXT_PUBLIC_CLIENT=cress` (défaut) ou `tlst` dans `.env` choisit l'habillage et le vocabulaire (`config/clients/`) ; `npm run seed:tlst` charge la petite démo TLST (`NEXT_PUBLIC_CLIENT=tlst npm run seed -- -- --skeleton` : squelette seul). `npm run check:vocab` vérifie qu'aucun mot du vocabulaire n'est en dur ; `npm run test:unit` teste les fichiers clients et les helpers.
4. `npm run dev -- -p 3001` — ouvre http://localhost:3001 (3000 est pris par un autre projet sur le poste de Gaël). **Connexion** : chaque personne du seed a `prenom.nom@exemple.fr` (accents retirés, ex. `claire.vasseur@exemple.fr`) et le mot de passe commun `pilote-demo-2026` (`DEMO_PASSWORD` au seed). Avec `PILOTE_DEMO=1` dans `.env`, le menu utilisateur en haut à droite garde « Changer d'utilisateur » pour prendre la place d'une autre personne et ses droits. Pas de mail dans le prototype : les liens « mot de passe oublié » et « compte créé » vont dans la boîte d'envoi (Admin › Comptes). Les droits de chaque rôle se règlent dans Admin › Rôles et droits (catalogue `lib/permissions.ts`).
5. `npm run lint && npm run build` — vérifications ; `npm test` — 95 tests Playwright (≈ 5 min ; projet `chromium` sous `cress`, projet `tlst` = `tests/habillage.spec.ts` sur un second serveur `PW_PORT+1` et la base `pilote_test_tlst`, à créer une fois ; `npx playwright test --project chromium` évite le build TLST) sur leur propre **serveur de production** (`next build` + `next start`, port `PW_PORT`, 3100 par défaut, `.next-test`) et **leur propre base** `pilote_test` (`TEST_DATABASE_URL`), migrée et reseedée à chaque suite : le serveur de dev 3001 n'est plus touché. `PW_DEV=1 npx playwright test tests/x.spec.ts` garde le serveur de dev (itération rapide, serveur réutilisé). Deux suites en parallèle : changer `PW_PORT` et `TEST_DATABASE_URL`.
6. `npm run screenshots` — une capture par écran dans `docs/screens/`.

Démo en ligne : https://cress.bazixx.fr (rideau `auth_basic`, voir `deploy/README.md`) ; mise à jour par `./deploy/deploy.sh cress` (une instance par client : `deploy/instances/`) (Postgres du VPS : rôle, base et sauvegarde `pg_dump` gérés par le script).

Docs : `CLAUDE.md` (brief), `docs/charte.md`, `docs/decisions.md`, `docs/chiffrage.md`, `docs/integrations.md`, `docs/evolutions.md`. Tests : trois recettes, une simulation collective à six personas, le flux agenda, les pièces jointes, les conventions, le périmètre, la revue UX, les tâches, les financeurs, les remarques de fiche, le plan de charge, les versements, les appels à projets et les modules par installation, la matrice qui-finance-quoi et le lexique, le réalisé comptable importé, les comptes et la connexion, les rôles et droits, la fiche personne et le départ, l'annuaire des organisations, les contacts et leurs listes. Les pièces déposées vont dans `uploads/` (hors git).
